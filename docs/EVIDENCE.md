# RakshaCall Tamper-Evident Evidence Vault

## 1. Hash Chain Specification

Each incident session produces an unbroken, immutable cryptographic chain:

```
[ Genesis Block ] ➔ Hash: H_0
       │
       ▼
[ Event 1: Authority Impersonation ]
   - previousHash: H_0
   - currentHash:  H_1 = SHA256(H_0 : id_1 : t_1 : TACTIC : s_id : payload_1)
       │
       ▼
[ Event 2: Isolation Tactic ]
   - previousHash: H_1
   - currentHash:  H_2 = SHA256(H_1 : id_2 : t_2 : TACTIC : s_id : payload_2)
       │
       ▼
[ Event 3: Payment Demand ]
   - previousHash: H_2
   - currentHash:  H_3 = SHA256(H_2 : id_3 : t_3 : TACTIC : s_id : payload_3)
```

## 2. Integrity Verification Workflow

When a user or investigator opens a session in the Evidence Vault:
1. `VerifyEvidenceIntegrityUseCase` queries all `EvidenceEvent` records ordered chronologically by timestamp.
2. It recalculates the SHA-256 digest of each event starting from the genesis block.
3. If all hashes match: returns `IntegrityResult.Valid` displaying the green **`TAMPER-EVIDENT INTEGRITY VERIFIED (SHA-256)`** badge.
4. If any event has been tampered with: returns `IntegrityResult.Failed(compromisedEventId, reason)`.

## 3. Incident Export Formats
- **JSON**: Machine-readable chronological export with full hash chain metadata for forensic analysis.
- **Plain Text**: Formatted for direct inclusion in formal police complaints (Cyber Crime 1930 / `cybercrime.gov.in` FIR filings).
- **Disclaimer**: Every report clearly states: *"Generated by RakshaCall for incident organization and preservation. Evaluated based on on-device observed patterns."*
